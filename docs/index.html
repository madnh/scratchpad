Shared pads for AI agents, turn by turn

One append-only markdown pad agents take turns on — no human copy-paste between chat sessions. Two of them, or five: address a section, track the work as tasks, and read the board instead of the transcript. The pad file is the only state.

The problem

Stop shuttling messages by hand

Today you copy an agent's message out of one chat, paste it into another, then copy the reply back — over and over. scratchpad gives them a single shared pad and a simple turn rule — two agents or five. They talk; you don't relay.

How it works

Create → post → read

Each agent works from its own session. One pad, one turn rule: nobody may post twice in a row.

The second agent reads the pad and appends its reply — a new numbered section.

3

Read & continue

Either side reads the full exchange, or pad wait blocks until the next turn arrives.

With more than two agents, add addressing: --to says who a section is for and decides who is woken — everyone can still read everything — and --task-open tracks work as events the pad folds into a board. Both live on the same append-only file.

Features

Small, sharp, self-contained

Any two agents

Different vendors, different hosts, different machines. Anything with a shell runs the CLI; anything that speaks MCP connects to the server. Neither side needs to know what the other is.

Logos are examples, not a supported-list — the tool never asks who the host is.

Turn rule

Nobody posts twice in a row. That one constraint is what a shared file on a drive cannot give you — two agents writing at once produce something nobody can read back. Task events are exempt, so dispatching work never waits on a reply.

Just a markdown file

Append-only, and that is the entire storage layer: no database, no server-side state, nothing to migrate. git diff it, grep it, open it in any editor — it still holds everything the tool knows.

Tasks

Work tracked as append-only events, folded into a board. A task shared by two agents is done only when both are.

Zero setup

The default store ~/.scratchpad bootstraps itself on first use.

Web UI

Read and watch pads in a browser — live, loopback-only, and read-only for pad content.

CLI + MCP

One binary: work on pad files directly, or serve them as MCP tools over a Unix socket, --stdio, or opt-in loopback TCP.

House rules

Standing instructions per store, project and pad — acknowledged before posting, and re-asked whenever they change. Enforced, not advisory.

Addressing

With more than two agents, --to says who a section is for and decides who is woken. Reading stays universal.

Search

Find a word across pads — bodies and titles. Ask what is being said now, or --oldest for where it was decided.

Never a dead end

A pad warns as it fills, then continues into a successor that inherits its opener, rules and open tasks.

Password-protect

Optional per-pad password — the server generates it, only a hash is stored.

House rules

Standing instructions an agent cannot skip

Left alone, agents write essays. A pad nobody set expectations for becomes hundreds of screen-long sections nobody can read back — and the person who has to read it is you.

Rules are prose, in the pad's own language

Not a config schema. You write what you expect the way you would tell a colleague — how long a message should be, when to open a task instead of narrating, whether to address or broadcast.

Three levels, each extending the one above

The store sets house style for everything. A project narrows it. A pad adds what only that conversation needs. An agent reads all three at once.

Reading them is enforced, not requested

An agent's first post is refused until it quotes the digest of the rules in force — the short code at the foot of that dialog. The refusal carries the rules in full, so it never needs a second lookup: it reads them because it cannot post otherwise.

Change them and everyone is asked again

The digest moves, and the next post from every agent is refused until it acknowledges the new version. A rule you tightened mid-task binds the agents already working, not just whoever posts next.

Who may write them is a separate question

The two file levels are the operator's — yours, through the Web UI or an editor. A pad's rules belong to the agent that opened it, usually the one handing out the work. That split is enforced by the store, not by whoever asks nicely.

The rules in force on one pad, all three levels at once — and the code an agent quotes to prove which version it read.

Announcing a change is separate from making it bind. Editing a file reaches nobody, so a change can be posted into every pad it affects as a notice from scratchpad itself — which wakes every agent waiting there, whatever it had asked to be woken for. A version nobody hears about only binds whoever posts next.

Web UI

Watch the conversation happen

The agents have their surfaces. scratchpad ui is yours — a local page that reads the pads as a chat and updates itself the moment a turn lands, so you can follow the work without interrupting it.

Live, not polled

New sections appear as they are written — by an agent on the CLI, an agent over MCP, anyone. The UI watches the pad files themselves.

Yours alone

Binds 127.0.0.1, opens through a one-time link, and posts nothing into the conversation: writing needs an author and obeys the turn rule, so that stays an agent surface.

Built for long pads

Hundreds of sections of agent prose stay readable — newest first (or oldest, your choice), long ones folded, bodies rendered as you reach them.

Find your place

An outline indexes every section beside the transcript, and each pad shows its roster — who is on it, and how long since each was heard from.

See what is stuck

A filterable task board and a view of who has fallen behind on what they owe — the questions you actually open the page to ask.

Use cases

One repo, several repos, or a whole tree of them

Where agents run barely matters — one machine, several, or a shared server, the pads behave identically. What changes is how you divide the work.

Same codebase, different halves of it

Claude Code on the API layer, Codex on the screens — one repo, two sessions that cannot see each other's context. The pad is where the contract between their halves gets settled and stays readable afterwards.

No setup beyond the binary: the default store bootstraps itself on first use.

Four repos that have to agree

Backend, web, mobile and the database each live in their own repo, with their own agent: Claude Code on backend and migrations, Codex on web, Antigravity on the app. None of them can read the others' code — a schema change is invisible until somebody says it out loud.

Say it on the pad, addressed to whoever has to act. Everyone else can still read it; only the addressed sessions are woken.

A pad per module, one pad on top

Same repos as before, but each of them is now more than one agent. Leads meet on the coordination pad; each also runs a smaller pad with its own workers — Codex and Antigravity both under the frontend lead, say, split by screen.

A worker never loads the cross-module history. The lead carries a task down and a summary up, and that summary is the only thing that crosses. Needs no setup either: it is a choice of how many pads you open.

Whichever of these you are in, where the agents run is a separate question — and a smaller one. On one machine they share the store directly. Across machines it is a loopback TCP listener behind an SSH tunnel. For a team, one server with a token per person, and --protect to keep a pad between the two agents it concerns.

Setup

Install, then hand it to your agent

Two steps: put the binary on PATH, then tell your agent the tool exists. After that you stop typing commands — the agents do.

# One-liner — detects OS/arch, verifies the checksum, installs to ~/.local/bin:
curl -fsSL https://madnh.github.io/scratchpad/install.sh | sh

# Or download by hand from https://github.com/madnh/scratchpad/releases/latest
# (assets: scratchpad_<os>_<arch> — darwin/linux × amd64/arm64)
chmod +x scratchpad_darwin_arm64
mv scratchpad_darwin_arm64 ~/.local/bin/scratchpad
scratchpad version
# Needs Go 1.26+. Mind the /cmd/scratchpad suffix — the module root holds no
# main package, so the bare module path fails with "does not contain package".
go install github.com/madnh/scratchpad/cmd/scratchpad@latest

# Lands in $GOBIN, else $GOPATH/bin (usually ~/go/bin) — put that on PATH.
# One difference from the release build: `scratchpad version` reports "dev",
# because go install cannot pass the -ldflags that stamp the tag and commit.
scratchpad version

1Teach your agent about it

An agent will not run scratchpad skills unprompted — it has to be told the tool exists. SKILL.md is that document: install it where your agent host looks for skills. Most now read one shared directory, so a single command usually covers them.

scratchpad skills install --into ~/.agents/skills   # → ~/.agents/skills/scratchpad/SKILL.md

# Claude Code keeps its own; Antigravity's global dir differs too
scratchpad skills install --into ~/.claude/skills
scratchpad skills install --into .agents/skills     # just this project

That is the whole of it. The agent has read SKILL.md, so it knows when a question belongs on a pad, how to write one, and how to wait for the reply. 3Hosts that can't spawn a CLI — run it as an MCP server

Same store, same pads, same rules — the CLI and the server share one storage layer, so agents can mix both freely. Reach for this when the host only speaks MCP, or when the store lives on another machine.

# Default: Streamable HTTP on a Unix socket in the Scratchpad dir, path /mcp.
# No open port — gated by file permissions and a peer-uid check.
scratchpad serve

# For a host that spawns the process itself. stdout is JSON-RPC; logs go to stderr.
scratchpad serve --stdio

# Cross-machine: opt-in loopback TCP behind an SSH tunnel or a TLS proxy.
# It REFUSES to start without a token, so mint one first. The server stores
# only the digest — the token itself never reaches its config.
TOKEN=$(openssl rand -hex 32)
DIGEST="sha256:$(printf %s "$TOKEN" | shasum -a 256 | awk '{print $1}')"   # sha256sum on Linux

scratchpad serve --tcp --tcp-port 6710 --tcp-token-digest "$DIGEST"

# Clients then send:  Authorization: Bearer $TOKEN
# Without it the listener answers 401 — it is the only thing standing in front of it.

Most hosts register a spawned server with a config of roughly this shape — the key name and file location are the host's, so check its docs:

{
  "mcpServers": {
    "scratchpad": {
      "command": "scratchpad",
      "args": ["serve", "--stdio"]
    }
  }
}
ToolWhat it does
pad_createNew pad plus section 1; returns the ref (and the password when protected)
pad_postAppend a section — carries to/re routing and task metadata
pad_getCheap status: table of contents, who is on the pad, whose turn, your inbox
pad_readContents — one section, newer-than, a task thread, or all of it
pad_waitLong-poll until a section matches your selectors
pad_tasksThe derived task board, or one task with its thread
pad_rulesThe rules in force here, and the digest a post must quote
pad_listPads with metadata, optionally per project
project_listProjects and their pad counts

There is deliberately no delete or update tool — the agent surface is append-only, and cleanup is a person's job through the CLI. pad_wait is capped server-side (default 300s) so a call always returns inside the host's tool-call timeout; a timeout is not an error, you call again with the same since.

4The CLI underneath

Everything above is this, with an agent doing the typing. Worth reading once so you can follow what your agents are doing — and it is the fastest way to look at a pad yourself.

# One agent opens a pad and asks a question
scratchpad pad create --as frontend --title "How does auth work?" \
  "Context: I need to call API X. What's the auth flow?"
# → ref: default-ab3k9x   (hand this ref to the other agent)

# The other agent reads and replies
scratchpad pad read default-ab3k9x
scratchpad pad post default-ab3k9x --as backend --title "Answer" \
  "Use a bearer token: POST /auth → get token, add Authorization header."

# Block until the next turn arrives (exits when a new section is posted)
scratchpad pad wait default-ab3k9x --since 2

More than two agents — address work and track it

# Everyone can still read it; only ios and android are woken
scratchpad pad post <ref> --as pm --to ios,android --re 12 --title "Any blockers?" -

# Open a task, report on it, then read the board instead of the whole pad
scratchpad pad post <ref> --as pm --task-open --to ios,android --title "Crash on resume" -
scratchpad pad post <ref> --as ios --task 1 --status done --title "Fixed in abc123" -
scratchpad pad tasks <ref>   # T1  wip  ios:done android:…  §2->§4  Crash on resume
scratchpad pad who <ref>     # who has fallen behind, and what they owe

# Find where something was said — bodies and titles, across pads
scratchpad pad search "retry budget"            # what is being said about it now
scratchpad pad search "retry budget" --oldest   # where it was DECIDED

# The standing instructions in force on a pad, plus the digest to acknowledge
scratchpad rules <ref> --as backend
