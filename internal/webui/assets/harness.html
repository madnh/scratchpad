Transcript harness

Measures what happens to transcript rows when the page re-renders: whether a row is kept or rebuilt, whether a parsed body stays parsed, whether an expanded section stays expanded, and whether the reader's place moves.

How to run it

  1. Start the UI against a store with a pad worth reading — one with more than 20 sections, and at least one section over 1200 bytes, or nothing will be clamped and criterion 3 has nothing to test: scratchpad ui --dir ~/.scratchpad-demo --no-auth.
    Without --no-auth, open the app's one-time link first so this page inherits the session cookie — it calls the same API.
  2. Open this page at /harness.html?ref=<project>-<padid>, or type the ref below and press Mount.
  3. Press Baseline. That records every row's node identity, every body's parse identity, every lazy element's state, and where the topmost visible section sits.
  4. Do ONE thing, then read the report. The buttons below drive the app's own controls and report themselves after a moment. The one thing they cannot do is post — the UI is read-only for pad content, deliberately — so for the case that matters most, post from a shell and then press Report:
    scratchpad pad post <ref> --as someone --title "x" "y"

"Rows rebuilt: 0" does NOT mean the reader's state survived. It means the engine did not rebuild the node. It says nothing about whether the node was MOVED — and a move is insertBefore, which the DOM defines as remove-plus-insert, so anything the browser keeps on the element goes with it. Focus is the case that bites: a row can survive a filter, keep its identity, and still lose focus to <body>, throwing a keyboard reader to the top of the document while every count on this page reads clean. Which rows get moved is a property of the DIFF, not of the action — removing rows so the survivors are no longer adjacent relocates them exactly as a reorder does.
That is why focus is measured separately below, and why a run where nothing was focused says so instead of staying quiet: an absent FAIL must not read as a PASS. The state that DOES survive here — whether a section is expanded — survives because it was deliberately moved out of the DOM into JS, not because the node was kept.

Re-parse on a flip is known and is not a regression. Flipping the order MOVES rows rather than rebuilding them, and moving a node reconnects it; <puredashboard-markdown> re-renders in its connectedCallback, so it parses again. Before this harness's subject existed, a flip rebuilt every row instead. A non-zero count here means the move path, not a broken keyed list — check rows_rebuilt, which should still be 0.

The held-section shift is only meaningful for "load older". Reading newest-first, a section that arrives lands ABOVE what you are reading and is supposed to push it down; the shift then measures the new section's height, not a defect. Reading oldest-first, an older page also lands above — and there the number must be 0, because the reader did not ask to move.
It is also thrown off by anything that scrolls the page in between, including clicking or focusing a control up here — the report says held_shift_trustworthy: false when that happened, and you should re-take it rather than read the number.

Numbers are comparable between runs of this harness, not with the app's own window. There is no sidebar here, so the column is wider and every wrapped body is shorter. Differences (shift, counts) carry over; absolute pixel heights do not. Sample sizes are yours to choose: one run of anything near a noise floor — the load-older shift especially — settles nothing.
